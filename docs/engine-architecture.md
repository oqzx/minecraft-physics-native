# Architecture

How a tick gets from a caller to a release's rules and back. This page names what exists. A limitation is marked as one.

## Layers

```
caller
  |  direct: LoadNativePhysics()          bot: createBotPhysics(bot), createNativePhysics(registry)
  v                                        v
src/native.ts (the loader)             src/mineflayer (adapter: NativePhysics, one class per release)
  |                                        |  NativeWorldSync, a packed Float64Array, setState
  v                                        v
native/artifacts (N-API addon, or WASM on the emnapi runtime)
  |
  v
native/src/napi_*.rs (objects and packed arrays to Rust state; validation)
  |
  v
native/src/versioned/mod.rs dispatch(version, ...)  ->  v-<release>.rs  Engine + Profile
  |
  v
shared simulation: simulation.rs, player.rs, collision.rs, entity.rs, vehicle.rs, ridden.rs, projectile.rs, ...
  |  reads
  v
world.rs WorldSnapshot (blocks the caller wrote)     native/data/releases, native/data/shapes (generated tables)
```

## Who selects the release

There is one selected release per call or per engine. Nothing picks the nearest release.

| Layer | Where | How |
| --- | --- | --- |
| Inventory | `native/src/versioned/mod.rs` `SUPPORTED_VERSIONS` | 50 entries. `is_supported` checks an exact string |
| TypeScript list | `src/versions.ts`, generated by `scripts/generate-version-exports.cjs` | `test/version-registry.test.cjs` keeps it equal to the Rust list |
| Engine classes | `src/mineflayer/versions.ts`, generated by `scripts/generate-version-exports.cjs` | `NativePhysics_<release>`, `NATIVE_PHYSICS_ENGINES`, `createNativePhysics(registry)` |
| Vehicle engine classes | `src/mineflayer/vehicle-versions.ts`, generated by `scripts/generate-vehicle-engines.cjs` | `createNativeBoatPhysics`, `createNativeRiddenMobPhysics` |
| Registry check | `src/mineflayer/registry-release.ts` `resolveRegistryRelease` | The registry must declare the selected release. `docs/registry-release-contract.md` |
| Rust dispatch | `dispatch` in `native/src/versioned/mod.rs` | A `match` on the exact string. `tick_conforming` refuses a profile that breaks its behaviour contract |
| Parity refusal | `src/release-status.ts` `assertReleaseAdmitted`, `requireParity: true` | Refuses a release that is not admitted. Today that is all of them (`docs/release-status.md`) |

## Rust profiles and shared code

Each `native/src/versioned/v-<release>.rs` has an `Engine` and a `Profile`. The profile's `rules()` gives a
`VersionPhysicsRules`: gravity, drags, fluid scales and policy flags. `Engine::tick` calls a `tick_with_profile*` function
of `native/src/simulation.rs`. So a release has its own constants and its own entry, and runs shared code.

Shared code holds the other differences, as `release.at_least(...)` gates. `generated/shared-gates.json` lists each gated
function, and `docs/version-gates.md` each boundary. Sharing a path does not show that vanilla is the same on both sides of
it: `docs/shared-code-audit.md` says what was compared and marks the rest `unverified`.

| Concern | Lives in |
| --- | --- |
| A release's constants and policy flags | `native/src/versioned/v-*.rs` |
| Policy read from the version alone, checked against the profile | `VersionBehaviorContract` in `native/src/versioned/mod.rs` |
| Behaviour gates inside algorithms | shared modules, `release.at_least(...)` |
| Block, fluid, tag and shape tables per release | `native/data/`, generated |
| Movement constants | `generated/movement-sites.json` (each literal by function, its proof, its Java type, its releases), `generated/movement-constants.json` and the profiles |

## A direct tick

`simulateVersionedTick('1.21.11', world, state, config)`, as in the README:

1. `LoadNativePhysics` in `src/native.ts` loads `native/artifacts/native.js`, which picks the addon or a WebAssembly build.
2. `simulate_versioned_tick` in `native/src/napi_api.rs` takes the scene out of the state (`LocalPlayerScene::take`:
   nearby entities, rockets, moving pistons), converts the rest to `SimulationState`, parses the version and validates
   the config.
3. `LocalPlayerScene::tick` runs the scene in order, with `versioned::dispatch` for the player's own tick. The version
   string selects `Engine` and `Profile`.
4. The tick reads `world`, the caller's `NativeWorld`. The exact data is what the caller wrote with `setFullBlock`,
   `applyBlockUpdates` and the like. The generated tables are read by the release's helpers (`generated*` exports) and by
   the engine's fluid and tag rules.
5. The result comes back as a new `NativeSimulationState`. The binding keeps nothing between calls but the world.
   `simulateVersionedTickOutcome` returns what the next tick needs (`docs/state-contract.md`).

## An adapter tick through EPhysicsCtx.FROM_BOT

`createBotPhysics(bot)`, `setup.context(EPhysicsCtx)`, `setup.physics.simulate(ctx, bot.world)`, `ctx.state.apply(bot)`:

1. `createBotPhysics` in `src/mineflayer/setup.ts` calls `createNativePhysics(bot.registry)`, which takes the class of the
   registry's release. For a bot on a data-alias release it passes `bot.version`. A bot on another release is refused.
2. `NativeEngine`'s constructor in `src/mineflayer/base.ts` resolves the release, refuses it if `requireParity` asks and it is
   not admitted, loads the binding and checks `isSupportedVersion`.
3. `setup.context` calls `factory.FROM_BOT(physics, bot)` of `mineflayer-physics-util`, which makes a `PlayerState`. The
   adapter adds the counters that state lacks on the first tick.
4. `NativePhysics.simulate` in `src/mineflayer/player.ts` checks that a sync can read the move (`syncReads`). If not, it
   sets `state.moveRefused` and skips the tick (`docs/numeric-contract.md`).
5. `tick` runs the decisions of `LocalPlayer.aiStep` in TypeScript: riptide launch, fluids, swimming, crouch, sprint, fly.
6. `NativeWorldSync.sync` in `src/mineflayer/world.ts` brings the blocks the tick can reach (`reachOf`) into the engine's
   `NativeWorld`, using the release's `BlockMapper` (`src/mineflayer/blocks.ts`, `src/mineflayer/legacy.ts`).
7. `carryFor` finds the state's `NativePlayer`. Rare fields go by `setState`. The rest go in the packed array of
   `NativePlayerInput`, by `scripts/state-bridge.cjs`'s classification.
8. `NativePlayer.tickMove` in `native/src/napi_player.rs` runs the release given to its constructor up to the pose update.
   The adapter picks the pose, and `finishTick` runs what ticks after the player. The output comes back as
   `NativePlayerOutput`, which `takeOutput` writes to `PlayerState`.
9. `ctx.state.apply(bot)` belongs to `mineflayer-physics-util`, and is the caller's to call.

Vehicles, projectiles and moving entities go through `src/mineflayer/vehicles.ts`, `src/mineflayer/projectiles.ts` and
`src/mineflayer/moving-entities.ts`. These sync the world the same way and call the matching `simulateVersioned*` entry
points with object states, not a packed array.

## Who owns what

| State | Owner | Lifetime |
| --- | --- | --- |
| The player's state in the object API | the caller | Handed in and out on every call |
| A `NativePlayer`'s state | the `NativePlayer`, seeded by `setState` | Until the next `setState` (`docs/state-contract.md`) |
| The adapter's carry | `NativePhysics.carries`, a `WeakMap` keyed by state | As long as the `PlayerState` |
| A `NativeWorld` | the caller, or its `NativeWorldSync` | A sync replaces it on a new source, or when its cache passes its limit |
| A sync, its moving blocks and shulker lids | the engine's `WorldLink` | Until `releaseWorld`, `dispose`, or the bot's `end` |
| Scene order | the caller | One tick: `nearbyEntities` and `ticksBeforePlayer`, in tick order (`docs/boundary-inputs.md`) |

## Generated data

| Input | Generator | Output |
| --- | --- | --- |
| Pins of sources and jars | `scripts/source-pins.cjs`, `scripts/materialize-sources.cjs` | The trees the generators read |
| Mojang's list | `scripts/generate-mojang-releases.cjs` | `generated/mojang-releases.json` |
| Version manifests and source records | `scripts/generate-version-manifest.cjs`, `scripts/generate-release-manifest.cjs` | `generated/minecraft-versions.json`, `generated/release-manifest.json` |
| Block classes, states, tags, shapes, fluids, entities | The stages of `scripts/generate-all.cjs` | `generated/*.json`, `native/data/` |
| Running clients' registries | `scripts/generate-runtime-registries.cjs` | `generated/runtime-registries.json` |
| The admission's evidence | `scripts/release-admission.cjs --write` | `src/release-status.json` |

Data splits at two paths. Six legacy releases, 1.8.8 to 1.13.2, come from `generated/legacy-release-data.json` and yarn-named
trees. The 44 from 1.14.4 come from the release manifest's pinned sources. `docs/release-build.md` has the pins, and
`docs/source-records.md` the record of each release.

## Where a change must propagate

A new field of the player's state:

1. `SimulationState` in `native/src/simulation.rs`.
2. `NativeSimulationState` and its conversions in `native/src/napi_api.rs`.
3. If it is packed, a slot or flag in `native/src/napi_player.rs` and `src/native.ts`, with a new layout version.
4. A channel in `scripts/state-bridge.cjs`. `test/state-bridge.test.cjs` fails without it.
5. `NATIVE_SIM` in the recorder's `schema/fields.ts`. `tsc` fails without it, as the map is typed over every key.
6. A row in `docs/state-contract.md`, whose test fails without it, then `node scripts/field-catalogue.cjs`.
7. If the adapter owns its value, `src/mineflayer/player.ts`.

Other public fields follow the same path through their own binding file, then `docs/field-maps.md` where the interface
is mapped there, and the catalogue.

A new release:

1. Its `native/src/versioned/v-<release>.rs`, and its place in `native/src/versioned/mod.rs`.
2. Its inputs in `scripts/source-pins.cjs`, then `scripts/generate-all.cjs`.
3. `scripts/generate-version-exports.cjs` and `scripts/generate-vehicle-engines.cjs`, which write the TypeScript lists and classes.
4. The recorder's `mod/mc/<release>`.
5. `scripts/release-admission.cjs --write`, `scripts/release-status-doc.cjs`, a row in `docs/recorder-coverage.md`.

`scripts/verify-version-coverage.cjs` and `test/version-registry.test.cjs` check the lists. The steps above are read from the
scripts. A real new release has not been added through this list.

## Current limitations

These are how the code is today, not the intended contract.

- `simulateBoatTick`, `simulateHorseTick`, `simulateProjectileTick`, `simulateArrowTick` and `simulateTridentTick` take no
  version. They run at the default release (`VersionPhysicsRules::default()`) and do not select one of the 50. Only
  `simulateTick` and `simulateTicks` refuse. Use the `simulateVersioned*` forms.
- A data-alias release runs the rules of its own release on another release's registry data. Each alias is proved, and the
  registry then declares another release than the engine (`docs/registry-release-contract.md`).
- `BlockMapper` and the adapter make decisions that have no Rust counterpart, so the object API and the adapter are two
  paths. `docs/state-bridge.md` says how far their equivalence is checked.
- B279 stays open: the construction checks are tested, and their verification over every integrated path has not been done.
- A vehicle has its own state and bridge. `docs/state-bridge.md` does not classify those fields, and `docs/field-maps.md` does.
